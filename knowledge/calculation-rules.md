# Правила расчётов: суммы, доли, балансы, переводы

Справка нужна, чтобы **независимо пересчитать** то, что приложение вернуло в
отчёт, и поймать расхождение.

**Проверено для версии:** `group-trip-expenses@2.0.0` (package.json).
**Дата проверки:** 2026-10-12.

---

## 1. Деньги хранятся в целых копейках

Все суммы в данных — целое число копеек (`amountKopecks`, `paid_kopecks`).
Рубли с копейками — только на входе и в отчёте.

- Источник: `src/lib/money.ts`, `toKopecks()` (строки 8–10), `toRubles()` (13–15).
- Повод перепроверить: в данных появилось дробное число копеек или в коде
  появился `parseFloat` в расчётах.

## 2. Формат записи суммы

`formatMoney()` даёт строку вида `1 234,56 ₽` (отрицательные — с `−`):
разряды разделяются **обычным пробелом**, перед `₽` — **обычный пробел**,
дробная часть через запятую, ровно 2 цифры.

- Источник: `src/lib/money.ts`, `formatMoney()` (строки 18–26).
- Повод перепроверить: кто-то «улучшил» формат до неразрывного пробела — из-за
  него уже ломались тесты, поэтому это известная зона риска.

## 3. Равное распределение: остаток по копейкам

`splitEvenly(total, n)`: каждому по `floor(total / n)`, остаток
`total mod n` добавляется **первым** участникам списка. Сумма долей всегда
равна исходной сумме.

- Источник: `src/lib/money.ts`, `splitEvenly()` (строки 42–51), `totalKopecksMod()` (53–55).
- Повод перепроверить: изменится порядок `participantIds` или способ
  распределения остатка.

## 4. Неравное распределение: доли обязаны сходиться

При `splitMode: "custom"` берутся `customShares[participantId]` в копейках; у
участника из списка, которому доля не задана, считается 0. Сумма долей должна
**точно** равняться сумме расхода, иначе запись отклоняется с кодом
`SHARES_MISMATCH`.

- Источник: `src/lib/calc.ts`, `getShares()` (строки 49–61),
  `validateCustomShares()` (108–116); `src/lib/service.ts`, `addExpense()`
  (проверка `SHARES_MISMATCH`, строки 232–239).
- Повод перепроверить: появится округление долей или допуск «сойдётся примерно».

## 5. Балансы

- `paid` — сколько участник реально заплатил: к сумме плательщика прибавляется
  **полная** сумма каждого расхода, где он плательщик;
- `owed` — сколько он должен был по своим долям во всех расходах, где он
  участник;
- `net = paid − owed`. Положительный `net` — участнику должны вернуть деньги,
  отрицательный — он должен доплатить;
- сумма `paid` по всем участникам равна сумме `owed` и равна общей сумме
  расходов (если все id корректны).

- Источник: `src/lib/calc.ts`, `calculateBalances()` (строки 10–43).
- Повод перепроверить: изменится знак конвенции `net` или учтутся расходы, где
  плательщик не входит в список участников (сейчас он всё равно «платит»).

## 6. Переводы: жадный алгоритм

Должники (`net < 0`) и кредиторы (`net > 0`) сортируются по убыванию суммы,
затем максимальный должник переводит максимальному кредитору минимум из двух,
пока обе стороны не закроются. Нулевые переводы не создаются. После всех
переводов балансы равны нулю с точностью до копейки; сумма переводов равна
сумме отрицательных балансов.

- Источник: `src/lib/calc.ts`, `calculateTransfers()` (строки 68–100).
- Повод перепроверить: смена алгоритма (например, на минимальное число
  переводов иным способом) — тогда ожидаемые пары «кто → кому» изменятся, хотя
  итог закрытия долгов останется верным.

## 7. Данные приложения не «чинятся» снаружи

`normalizeState()` отбрасывает расходы, ссылающиеся на несуществующих
участников, и объекты с некорректными полями. Если в отчёте и в источнике
расхождение — это повод сообщить о нём, а не подогнать число.

- Источник: `src/lib/service.ts`, `normalizeState()` (строки 31–58).
- Повод перепроверить: изменение правил отбраковки.

## Как быстро свериться без чтения кода

```bash
node tools/check-numbers.mjs --state data/<состояние>.json --report reports/<отчёт>.md
```

Скрипт пересчитывает пункты 1–6 сам (в копейках) и сравнивает с таблицами
отчёта.
